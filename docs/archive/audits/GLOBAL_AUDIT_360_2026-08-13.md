# NK DELIVERI — GLOBAL AUDIT 360°

**Date** : 2026-08-13
**Type** : Audit READ-ONLY (aucun code modifié, aucune migration appliquée, aucun commit/push)
**Méthode** : Lecture directe du code source (163 fichiers .tsx, 133 migrations), requêtes SQL **read-only** en direct contre la base de production (via l'API Management Supabase — `SELECT` uniquement, jamais d'écriture) pour construire une matrice RLS/policies/triggers réelle plutôt que déduite des migrations, inspection des specs Playwright E2E, CI, configuration Vercel/env.
**Confiance** : chaque affirmation est marquée **VERIFIED** (vu directement dans le code/DB), **PARTIALLY VERIFIED**, **INFERRED** (déduction raisonnable) ou **NOT VERIFIED** (hors de portée de cet audit statique — ex. scores Lighthouse réels, comportement live sous charge).

## 1. Executive Summary

NK Deliveri est une plateforme de livraison mature et **bien plus disciplinée que la moyenne** des projets de cette taille : 100% des tables `public` ont RLS activé (52/52, VERIFIED), une méthodologie de test transactionnel systématique pour chaque migration, une suite E2E Playwright réelle de 31 specs (auth, admin, client, driver, restaurant, cross-cutting incluant accessibilité WCAG et Lighthouse), 173 tests unitaires, des headers de sécurité HTTP solides (HSTS, X-Frame-Options, Permissions-Policy), et une séparation RPC/RLS globalement cohérente (`SECURITY DEFINER` + revérification de rôle indépendante + audit log).

Mais l'audit a trouvé **une vulnérabilité CRITIQUE réelle et vérifiée** : la policy RLS `"Admins manage roles"` sur `user_roles` permet à un `super_admin` d'écrire directement dans la table de rôles via PostgREST (`supabase.from('user_roles').insert/update/delete`), **contournant entièrement** le step-up MFA STRICT (TOTP obligatoire, 5 min) que ce projet a spécifiquement construit pour protéger `add_user_role_secure`/`remove_user_role_secure`. Une session super_admin volée peut donc s'auto-attribuer n'importe quel rôle sans jamais toucher TOTP. C'est le **problème n°1** à corriger avant toute nouvelle fonctionnalité.

Deux autres constats structurants : (1) le pipeline **CI ne fait tourner AUCUN test** (ni les 173 tests unitaires, ni les 31 specs E2E) — seulement lint/format/typecheck/build/migration-check — donc rien n'empêche une régression testée de fusionner sur `main` ; (2) **aucun Content-Security-Policy** n'est configuré nulle part (ni header Vercel, ni meta tag), alors que `dompurify` est présent dans le bundle, suggérant que l'équipe sait déjà qu'il existe une surface XSS à gérer mais n'a pas posé la couche de défense en profondeur correspondante.

En dehors de ces trois points, la plateforme est **techniquement fiable** pour son échelle actuelle (VERIFIED pour l'architecture DB/RLS ; INFERRED pour la charge réelle, non mesurée). Le système financier (wallet/commission/payout) est le mieux construit du projet — FIFO documenté, couverture partielle des commissions, traçabilité complète, aucune écriture directe RLS possible sur les tables financières sensibles (sauf `payments`, voir §9).

## 4. Critical Findings

### C-01 — RLS sur `user_roles` contourne entièrement le step-up MFA STRICT

**Domaine :** RBAC / Security
**Sévérité :** CRITICAL
**Confiance :** VERIFIED (requête live `pg_policies` + `pg_trigger`)
**Localisation :** table `public.user_roles`, policy `"Admins manage roles"` (migration d'origine des rôles), RPCs `add_user_role_secure`/`remove_user_role_secure` (`supabase/migrations/20260811120000_admin_step_up_enforcement.sql`)

**Preuve :**

```sql
-- pg_policies, table user_roles
policyname: "Admins manage roles"
cmd: ALL
qual: has_role(auth.uid(), 'super_admin'::app_role)
with_check: has_role(auth.uid(), 'super_admin'::app_role)
```

Aucun trigger n'existe sur `user_roles` (vérifié via `pg_trigger`, zéro ligne retournée). La seule protection est le rôle — pas de vérification `aal`/TOTP.

**Pourquoi c'est un problème :** `add_user_role_secure`/`remove_user_role_secure` appellent `private.require_admin_step_up_strict()` (TOTP obligatoire, 5 min, sans repli) — exactement la protection construite le 2026-08-11 contre le scénario "session admin volée → DevTools → RPC directe". Mais cette policy RLS ouvre un **second chemin d'écriture** sur la même table qui ne passe jamais par cette fonction.

**Scénario de reproduction :**

```js
// Avec une session super_admin (volée, XSS, ou simplement le navigateur
// resté ouvert), sans jamais toucher TOTP :
await supabase.from("user_roles").insert({ user_id: attackerId, role: "super_admin" });
```

Ceci réussit — RLS l'autorise, aucun trigger ne bloque, aucun step-up n'est demandé.

**Impact utilisateur :** aucun direct.
**Impact business :** compromission totale de la plateforme si une session super_admin fuit — accès à absolument tout.
**Impact sécurité :** contourne exactement le contrôle que ce projet a le plus soigneusement construit et documenté (`docs/ADMIN_ACCESS_SECURITY_REMEDIATION_REPORT.md`).

**Correction recommandée :** remplacer la policy `ALL` par une policy `SELECT` uniquement (les écritures ne passent alors QUE par les RPC), **ou** ajouter un trigger `BEFORE INSERT OR UPDATE OR DELETE` équivalent à `protect_delivery_status_transition` qui appelle `private.require_admin_step_up_strict()`. La première option est plus simple et cohérente avec le pattern déjà utilisé pour `orders`/`platform_payout_settings`/`payment_provider_settings` (zéro policy d'écriture directe, RPC uniquement).

**Priorité :** P0

### C-02 — Aucun test (unitaire ou E2E) ne tourne en CI

**Domaine :** Testing / DevOps / Reliability
**Sévérité :** CRITICAL
**Confiance :** VERIFIED (lecture directe de `.github/workflows/ci.yml`)

**Preuve :** Le job `quality` de `ci.yml` exécute exactement : `npm run lint`, `npm run format:check`, `npm run typecheck`, `npm run check:migrations`, `npm run build`. Le job `migrations-db` exécute `supabase start` (rejoue les migrations, pas les tests). **Aucune étape n'exécute `npm run test` (173 tests unitaires) ni `npm run test:e2e` (31 specs Playwright, dont accessibilité WCAG et Lighthouse).**

**Pourquoi c'est un problème :** ce projet a investi un effort réel et rare dans les tests (couverture des 4 providers de paiement, step-up MFA, hooks async) — mais rien n'empêche une PR qui casse ces tests de fusionner sur `main`. `npm run verify` (utilisé manuellement pendant les sessions de développement de ce projet) inclut bien `npm run test`, mais CI ne l'utilise pas.

**Scénario de reproduction :** faire une PR qui casse `moncash-webhook-handler.test.ts` (par exemple) → CI passe intégralement au vert → merge possible sans qu'aucun humain ne le remarque avant la prochaine session manuelle.

**Impact business :** régression silencieuse possible sur exactement les systèmes les plus sensibles (paiement, RLS/step-up, Komand).
**Correction recommandée :** ajouter une étape `npm run test` au job `quality`, et un job séparé (ou nightly) pour `npm run test:e2e` (Playwright nécessite un environnement navigateur + mocks Supabase déjà présents dans `e2e/support/mock-supabase.ts` — l'infrastructure existe déjà, il ne manque que le déclencheur CI).

**Priorité :** P0

## 5. High Findings

### H-01 — `payments.status` modifiable directement par un admin sans trigger de validation

**Domaine :** Payments / Business Logic
**Sévérité :** HIGH
**Confiance :** VERIFIED

**Preuve :** policy `"payments admin update"` (`cmd: UPDATE`, `qual: has_role(admin/super_admin)`, `with_check: null` → retombe sur `qual`). Triggers réels sur `payments` : `trg_notify_payment_status` (notifie le changement), `trg_payment_paid_confirm_order` (confirme la commande si `status='paid'`), `trg_pay_upd` (`updated_at`). **Aucun trigger n'équivaut à `protect_delivery_status_transition`** — rien ne valide qu'une transition de statut de paiement est légale, ni ne journalise l'action dans `audit_log`.

**Pourquoi c'est un problème :** un admin peut `supabase.from('payments').update({status:'paid'})` directement sans passer par `review_manual_payment_secure` (qui valide vraisemblablement la preuve de paiement) — les effets de bord (notification, confirmation de commande) se déclenchent quand même via trigger, ce qui masque le contournement (tout _a l'air_ normal côté client), mais sans validation ni entrée d'audit log attribuable à l'action réelle.

**Correction recommandée :** ajouter un trigger de validation sur `payments` (transitions légales + `private.log_audit_event`), sur le modèle de `protect_delivery_status_transition` — ou retirer la policy UPDATE directe et forcer 100% RPC comme pour `orders`.

**Priorité :** P1

### H-02 — Aucun Content-Security-Policy

**Domaine :** Security
**Sévérité :** HIGH
**Confiance :** VERIFIED (grep exhaustif : aucun header CSP dans `vercel.json`, aucun meta tag dans `__root.tsx`)

**Preuve :** `vercel.json` définit HSTS, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, COOP — mais aucun `Content-Security-Policy`. `dompurify` est présent dans le bundle de production (vu dans les logs de build de ce projet), ce qui suggère une conscience du risque XSS déjà présente côté sanitization d'entrée, sans la couche de défense en profondeur côté navigateur.

**Pourquoi c'est un problème :** sans CSP, une faille XSS (même mineure, même dans une dépendance tierce) a un blast radius maximal — exfiltration de session, injection de script arbitraire.

**Correction recommandée :** ajouter un header CSP (`vercel.json`), au minimum en mode `report-only` d'abord pour cartographier les sources légitimes (Supabase, Stripe, fonts, Leaflet tiles) avant de l'appliquer en `enforce`.

**Priorité :** P1

### H-03 — Dépendance à un serveur OSRM public de démo pour le routing GPS en production

**Domaine :** Maps/GPS / Reliability
**Sévérité :** HIGH
**Confiance :** VERIFIED (commentaire explicite du projet lui-même dans `.env.example` et `src/services/routing.ts` référencé)

**Preuve :** `.env.example` : _"Defaults to the public router.project-osrm.org demo server if unset — fine for development, but that demo server is rate-limited and explicitly not meant for production traffic."_ `VITE_OSRM_URL` n'a pas de valeur par défaut visible confirmant qu'un serveur dédié est configuré en production — **NOT VERIFIED** si la variable est réellement définie sur Vercel (hors de portée de cet audit statique).

**Pourquoi c'est un problème :** si `VITE_OSRM_URL` n'est pas configuré en production, le calcul d'itinéraire driver/tracking dépend d'un service tiers gratuit, non contractuel, rate-limité, susceptible d'être indisponible sans préavis — exactement au moment où la plateforme grossit (plus de commandes = plus de requêtes de routing = plus vite rate-limité).

**Correction recommandée :** confirmer en priorité que `VITE_OSRM_URL` pointe vers une instance dédiée en production ; sinon, c'est un risque de croissance immédiat.

**Priorité :** P1 (P0 si non configuré — à vérifier)

### H-04 — Incident SMTP total du 2026-08-11 découvert manuellement, pas par monitoring

**Domaine :** Observability / Reliability
**Sévérité :** HIGH
**Confiance :** VERIFIED (mémoire de session, incident réel de ce projet, corrigé le même jour)

**Preuve :** tous les nouveaux comptes (client/restaurant/driver) échouaient à l'inscription — mot de passe SMTP GoTrue invalide (erreur 535 niveau protocole). Trouvé et corrigé via investigation manuelle, pas via une alerte automatique.

**Pourquoi c'est un problème :** un blocage total de l'inscription est un des pires incidents possibles pour une marketplace en croissance (perte de 100% des nouveaux utilisateurs pendant toute la durée non détectée), et rien dans l'infrastructure actuelle n'aurait raccourci ce délai si l'investigation manuelle n'avait pas eu lieu ce jour-là.

**Correction recommandée :** alerte automatique sur le taux d'échec de `signUp()`/confirmation email (déjà partiellement possible via `newsletter_send_log`-style tracking, ou via Sentry si son DSN est réellement configuré en production — NOT VERIFIED).

**Priorité :** P1

### M-02 — `npm run verify` (local) et CI ne sont pas identiques

**Confiance :** VERIFIED. `verify` = typecheck+lint+check:migrations+test+build ; CI = lint+format:check+typecheck+check:migrations+build (+ migrations-db séparé). CI ajoute `format:check` (absent de `verify`) et retire `test` (présent dans `verify`). Un dev qui ne fait confiance qu'à `npm run verify` en local peut pousser du code non formaté qui casse CI, et croire à tort que ses tests unitaires sont vérifiés par CI. **Priorité : P2.**

`checkout.tsx` (630), `dashboard.admin.collect.tsx` (590), `dashboard.admin.payouts.tsx` (535), `komand-detail-dialog.tsx` (518), `dashboard.admin.finance.tsx` (509). **Confiance : VERIFIED** (wc -l). ### M-04 — Sentry optionnel, DSN production non vérifiable statiquement

Le code gère proprement l'absence de DSN (no-op), mais je ne peux pas confirmer si `SENTRY_DSN`/`VITE_SENTRY_DSN` sont réellement définis sur Vercel. **NOT VERIFIED — à confirmer par l'équipe.** Si absent, la plateforme n'a aucune observabilité d'erreurs runtime en production au-delà des logs. **Priorité : P1 si absent, sinon N/A.**

### M-05 — Pas de rôle "visiteur non connecté" explicitement testé pour les redirections deep-link

Les guards de rôle sont vérifiés au niveau layout (`beforeLoad`), pattern cohérent — mais je n'ai pas pu tester en live le comportement d'un accès direct à une URL profonde (`/dashboard/admin/payouts` sans session) au-delà de la lecture du code (`throw redirect`). **INFERRED correct depuis le code, NOT VERIFIED en conditions réelles.** **Priorité : P3.**

## 10. Business Logic Audit

Le state machine le plus critique du système — **`orders`** — est protégé à 100% par RPC (aucune policy d'écriture directe, VERIFIED). Le trigger `protect_delivery_status_transition` sur `deliveries` est un exemple de très bonne pratique : il valide les transitions légales (`assigned→en_route_pickup`, `picked_up→delivered`, etc. — liste blanche explicite, VERIFIED par lecture du code source de la fonction), interdit à un non-admin de réassigner une livraison ou modifier ses frais, et **synchronise automatiquement `orders.status`** en fonction de l'avancement de la livraison — une seule source de vérité, pas de risque de désynchronisation entre les deux tables.

**Concurrence :** `initiate_payout_secure` utilise `SELECT ... FOR UPDATE` sur le wallet avant de débiter (VERIFIED, lu dans la migration step-up) — protection correcte contre une double-dépense en cas d'appels concurrents.

**Risque de "deux actions concurrentes → état impossible" :** non trouvé sur les chemins examinés (orders, deliveries, payouts) grâce au verrouillage `FOR UPDATE` et aux triggers de transition. **NOT VERIFIED exhaustivement** sur l'ensemble des ~50 RPC métier (hors du temps disponible pour cet audit).

## 28. Final Recommendation — Réponses aux 10 questions finales

**1. NK Deliveri est-il techniquement fiable ?**
Globalement oui pour son échelle actuelle (RLS à 100%, tests réels, discipline de migration), mais avec un trou de sécurité CRITICAL actif et zéro filet de sécurité en CI. "Fiable avec un point aveugle sérieux à corriger avant de dormir tranquille" est le résumé honnête.

**2. Peut-il supporter une augmentation importante des commandes ?**
INFERRED probablement oui côté architecture DB (verrouillage `FOR UPDATE`, ledger append-only, réconciliation cron) — mais **NOT VERIFIED sous charge réelle**, et le risque OSRM (H-03) devient précisément PLUS dangereux avec plus de volume.

**3. Existe-t-il un risque financier ?**
Oui, modéré : H-01 (payments modifiable sans validation trigger par un admin). Le cœur du système financier (wallet/commission/payout) est en revanche solide.

**4. Existe-t-il un risque de sécurité critique ?**
**Oui — C-01, confirmé, à corriger en priorité absolue.**

**5. Existe-t-il des bugs pouvant bloquer une commande ?**
Aucun trouvé dans le state machine lui-même ; le module Komand existe précisément pour détecter ce cas s'il survient.

**6. Existe-t-il des états où l'utilisateur ne sait pas quoi faire ?**
Aucun dead state structurel confirmé ; risque potentiel non vérifié autour du tracking GPS si OSRM démo est utilisé en prod.

**7. Quelle partie est la plus fragile ?**
Le RBAC (C-01) et l'absence de filet de tests en CI (C-02) — pas le code métier lui-même, qui est solide.

**8. Quelle partie est la mieux construite ?**
Le système financier (wallet/commission/payout/FIFO) et la discipline de migration/RLS.

**9. Priorité absolue avant d'ajouter des fonctionnalités ?**
Fermer C-01 et C-02. Les deux sont rapides (quelques heures chacune), à fort impact, et ne demandent aucune refonte.

**10. Verdict de Principal Engineer ?**
Une plateforme construite avec un niveau de rigueur nettement supérieur à la moyenne pour sa taille — RLS exhaustif, tests réels, documentation vivante, discipline de migration transactionnelle. Mais la rigueur elle-même a créé un faux sentiment de sécurité sur `user_roles` : le step-up MFA a été bâti avec un soin extrême sur la couche RPC sans qu'un audit de la couche RLS parallèle ne confirme qu'aucun autre chemin d'écriture n'existait. C'est l'erreur classique d'une équipe qui sécurise fort sur un axe et oublie de vérifier les axes adjacents. Corrigez C-01/C-02, activez les tests existants en CI, et cette plateforme mérite une note nettement au-dessus de 70/100.
